# Contributing to QuickInspect

First off, thank you for considering contributing to QuickInspect. It's people like you that make QuickInspect a great element inspection tool.

## Where do I go from here?

If you've noticed a bug or have a feature request, make one! It's generally best if you get confirmation of your bug or approval for your feature request via [GitHub Issues](https://github.com/KostaD02/QuickInspect/issues) before starting to code.

## Project structure

```
_locales/
└── <code>/messages.json    # UI strings for one language; en carries the descriptions for translators
scripts/
├── i18n-report.ts          # pnpm i18n:report entry
└── i18n/                   # Locale checks and the coverage report behind it
src/
├── content/
│   ├── main.ts             # Content script entry: loads settings, wires the inspector
│   ├── inspector/          # Hold key, pointer, pin, copy and navigation state
│   ├── bridge/             # Main-world script: wraps addEventListener, answers event probes
│   ├── handover/           # Lets a newly injected content script retire the one already on the page
│   ├── host/               # Closed shadow root that isolates the UI from page CSS
│   ├── overlay/            # Margin / padding / content highlight and label
│   ├── panel/              # Floating info panel, plus panel.scss for the shadow root styles
│   ├── edits/              # In-place style, attribute and text edits with reset
│   ├── tokens/             # Declares the @kostad/brand tokens on the shadow root
│   ├── toast/              # Copy and status feedback
│   └── actions/            # Copy actions and their key bindings
│
├── popup/
│   ├── index.html          # Popup markup, built from @kostad/brand components
│   ├── main.ts             # Loads the bundled fonts and brand CSS, mounts PopupController
│   ├── brand.d.ts          # Module declaration for the brand stylesheet
│   ├── style.css           # The few rules @kostad/brand has no class for
│   ├── controller/         # Reads, writes and reflects settings
│   └── page/               # Reaches the active tab's content script, injecting it when missing
│
└── shared/
    ├── consts/             # APP_NAME, default settings, storage keys
    ├── types/              # Settings, ElementInfo, event, message and source types
    └── util/
        ├── a11y/           # Role and accessible name computation
        ├── selector/       # Short unique CSS selectors
        ├── xpath/          # XPath generation
        ├── locator/        # Playwright locator ranking and match counting
        ├── inspect/        # Builds ElementInfo (box, styles, attributes, media)
        ├── gaps/           # Gap areas between the items of flex and grid containers
        ├── dom/            # Shadow-aware hit testing and querying
        ├── events/         # Asks the main-world bridge for an element's listeners
        ├── source/         # Source markers, dev server detection and open-in-editor
        ├── sourcemap/      # Maps Vite and Next.js client positions back to the original file
        ├── format/         # px, hex colors, truncation
        ├── i18n/           # t(), plural(), localizePage() and the text direction
        ├── settings/       # Load, save, watch, normalise
        ├── clipboard/      # Clipboard writes
        └── logger/         # Prefixed console logging
```

Every folder under `content/`, `popup/` and `shared/util/` holds one module named after the folder, with its `*.spec.ts` beside it, so `inspector/` is `inspector.ts` and `inspector.spec.ts`.

## Setting up for local development

**Requirements:** Node.js 22+, pnpm

```bash
# 1. Clone the repository
git clone https://github.com/KostaD02/QuickInspect.git
cd QuickInspect

# 2. Install dependencies
pnpm install

# 3. Start the dev server
pnpm start
```

Then load the unpacked extension in Chrome:

1. Open `chrome://extensions`
2. Enable **Developer mode** (top-right toggle)
3. Click **Load unpacked**
4. Select the `dist/` folder generated by the dev server

The extension hot-reloads on file changes while `pnpm start` is running. The main-world bridge is the exception: it is built once on start, so run `pnpm build:bridge` after changing anything in `src/content/bridge/`.

## Build

```bash
pnpm build
```

The extension is written to `dist/` and zipped into `release/QuickInspect-<version>.zip`. `pnpm build:bridge` builds only the main-world bridge into the git-ignored `bridge/` folder.

## Linting and Testing

We use formatting and linting rules to keep the codebase clean. Please ensure your code passes our CI checks before submitting a PR.

- To check formatting (Prettier):
  ```bash
  pnpm format:check
  ```
  _(Or `pnpm format` to fix it)_
- To run the linter manually:
  ```bash
  pnpm lint
  ```
- To type-check:
  ```bash
  pnpm typecheck
  ```
- To run tests (Jest):
  ```bash
  pnpm test
  ```
  _(Or `pnpm test:watch` for watch mode, and `pnpm test:coverage` for the 80% coverage threshold CI enforces)_
- To check the locales and print the coverage table:
  ```bash
  pnpm i18n:report
  ```

Husky runs the format check, linter and tests before every commit.

## Translations

All user-facing text lives in `_locales/<code>/messages.json` and reaches the UI through `chrome.i18n`: `data-i18n` attributes in the popup HTML (`data-i18n-html` for markup, `data-i18n-attr` for attributes), filled by `localizePage()` before the controller runs, and `t()` / `plural()` from `src/shared/util` in TypeScript. English is the default locale and the only file with `description` fields, which tell translators where a string appears. The main-world bridge has no `chrome.i18n`, so it only reports data (function names, flags, framework names) and the panel words it in the isolated world.

To add or fix a language:

1. Copy `_locales/en/messages.json` to `_locales/<code>/messages.json`, using one of Chrome's [supported locale codes](https://developer.chrome.com/docs/extensions/reference/api/i18n#locales).
2. Translate the `message` values. Keep the `$PLACEHOLDER$` tokens and the `<strong>` and `<kbd>` markup as they are, including the key letters inside `<kbd>`, and keep `appName` within 45 and `appDescription` within 132 characters, the limits Chrome puts on the manifest. Tag names, CSS property names and pixel values are not messages and stay untranslated.
3. Messages that count things come in plural forms (`listeners_one`, `listeners_other`). Provide every form your language uses according to the [CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules): `other` is always required, Polish or Russian also need `few` and `many`, Arabic needs all six.
4. Run `pnpm i18n:report`. It prints the coverage table, writes `tmp/i18n-report.md` and fails on missing plural forms, stray placeholders or markup that differs from English. CI runs the same script on every pull request and keeps the table in a sticky comment.
5. Load the unpacked build in a browser whose UI language is the one you translated, or start Chrome with `--lang=<code>`, to see the result in place. `pnpm test` also checks every locale against English.

Right-to-left languages (Arabic, Hebrew, Persian) flip the popup through `dir="rtl"` on the document and the panel through `dir` on its root element inside the closed shadow tree, both set from Chrome's `@@bidi_dir` message with a fallback on the UI language. `@kostad/brand` mirrors its components from that attribute on its own, so no RTL rules live in this repository; prefer logical properties (`margin-inline-start`, `text-align: end`) in any CSS added here. Selectors, code and page text sit in `<bdi>` elements inside the panel so they keep their own direction.

## Pull Requests

1. Create a new branch from `main` for your feature or bugfix.
2. Commit your changes. We use `commitlint` and `husky` to enforce [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Please format your commit messages accordingly (e.g., `feat: add a new locator strategy`, `fix: resolve panel position bug`).
3. Push to your fork and submit a Pull Request against our `main` branch. The PR title must follow Conventional Commits as well, since it becomes the commit message on merge.
4. Provide a clear and descriptive PR body detailing what the PR solves or implements.
